# Яндекс.Директ для промышленного B2B

Отработано на аккаунте PROM-EN (завод «Промышленная Энергетика», детали
трубопроводов для АЭС и ТЭС) в сентябре 2026: 11 старых кампаний заменены
семью новыми, найдено и остановлено около 350 000 ₽ годового слива.
Скрипты в `scripts/ads/`, подробный разбор — в `PLAN-DIRECT.md`.

Порядок ниже проверен практикой. Он устроен так, что дорогие ошибки
ловятся до того, как потрачены деньги, а не после.

## Что менять под другую компанию

Скрипты писались под PROM-EN, и при переносе на другую компанию группы
надо заменить эти значения. Всё остальное — методология и обвязка API —
работает как есть.

| Что | Где | Как узнать |
|---|---|---|
| Токен и логин Директа | `.env`: `YANDEX_DIRECT_TOKEN`, `YANDEX_DIRECT_LOGIN` | токен один на группу, логин у каждой компании свой |
| Счётчик сайта | `COUNTER` в скриптах | Метрика → настройки счётчика |
| Счётчик организации | второй в `COUNTERS` | `businesses.get` → поле `CounterId` |
| Организация | `BUSINESS` | `businesses.get` вернёт `Id`, `Name`, `Address` |
| Домен сайта | `SITE` | — |
| Разделы каталога и фасеты | `perf-reports/ads/<дата>/facets.json` | собирается обходом сайта, см. шаг 4 |
| Цели Метрики | `GOALS` в `direct_placements.py` | `management/v1/counter/<id>/goals` |
| Набор быстрых ссылок | `SITELINK_SET_ID` | создаётся заново, шаг 6 |
| Уточнения | `CALLOUTS` | `adextensions.get` покажет, что уже есть в аккаунте |

**Первым делом получите факты о компании, а не переносите чужие.** Годится
только структура работы, но не цифры: у другого завода другой каталог,
другие нормативы и другой спрос.

## Шаг 1. Что вообще в аккаунте

```bash
python scripts/ads/direct_api.py
```

Список кампаний, групп, объявлений и ключей. Смотреть в первую очередь:

* **сколько записей `---autotargeting`** — в старых аккаунтах это половина
  «семантики», и она искажает все подсчёты;
* **сколько групп на кампанию** — 800 групп по одной фразе означают, что
  кампания собрана генератором и не может набрать статистику;
* **состояние объявлений**: `OFF` — это «сейчас не показывается» (часто из-за
  пустого счёта), а не «остановлено». Остановлено — только `SUSPENDED`.

## Шаг 2. Куда уходят деньги

Расход и заявки по кампаниям, группам, площадкам и устройствам за год:

```bash
python scripts/ads/direct_audit.py --campaigns <id>
```

Считать заявки **по автоцелям формы, телефона и почты**, а не по всем целям
сразу: цель «Просмотр страниц» даёт сотни ложных срабатываний и делает
картину неузнаваемой. Так у PROM-EN «19 заявок» превратились в 2.

Обязательно проверить **глубину визита в Метрике** по типу площадки. Если
из сетей идут «заявки» при глубине ровно 1,0 страницы и 29 секундах — это
не заявки. Сравнивайте с поиском: там нормально 1,8 страницы.

## Шаг 3. Что чинить первым

По опыту PROM-EN, в порядке отдачи:

1. **Стратегия без потолка ставки.** `HIGHEST_POSITION` съела 255 000 ₽
   при 99 ₽ за клик. Смотреть `BiddingStrategy` у самых дорогих кампаний.
2. **Мобильные приложения в РСЯ.** 1 000 приложений дали 30 240 ₽ и ноль
   заявок. Лечится списком запрещённых площадок (потолок — 1 000 записей).
3. **Группы под запросы товара, которого нет в каталоге.** У PROM-EN
   627 фраз вели на трубы ГОСТ 20295, которых завод не возит.
4. **Минус-слова.** Проверить, есть ли «прайс», «бесплатно», «работа»,
   «б у», «своими руками». Заводить общим набором, а не в каждой кампании.
5. **Автотаргетинг.** По умолчанию включены все пять категорий. При точной
   семантике оставлять `EXACT` и `ALTERNATIVE`, остальные выключать.

## Шаг 4. Каталог: что можно рекламировать

Прежде чем собирать семантику, надо знать, что есть на сайте. Обойти
разделы и собрать значения фасетов:

```bash
python scripts/ads/site_facets.py --site https://example.ru
```

Скрипт сам находит разделы и подразделы и сохраняет карту фасетов в JSON.
Две вещи, которые он делает не в лоб и которые пришлось чинить на PROM-EN:

* **ищет пути по всему HTML, а не только в `href`** — на этом сайте адреса
  разделов лежат в data-атрибутах и JSON, и выборка по `href` нашла ровно
  одну ссылку из тридцати двух разделов;
* **отсеивает пагинацию, RSS и карточки товаров** — иначе обход уходит в
  `/catalog/page/514/` и в отдельные позиции.

Этот обход нашёл то, что я до него пропустил глазами: у труб и опор есть
**собственные подразделы** (`/catalog/truby/truby-bsh/` — 700 позиций,
`/catalog/opory/opory-skolz/` — 11), и они точнее фасета: своя страница,
свой заголовок, свой title. Вести группы надо туда, а не на витрину
с фильтром.

Три правила, оплаченные ошибками:

* **Счётчик позиций в HTML статичен.** Серверный ответ всегда показывает
  общее число раздела; реальную выборку фасета видно только в браузере.
  Проверять фасеты через `requests` бессмысленно.
* **Наполнение фасетов неравномерно.** У PROM-EN фасет ГОСТ 17376 отдавал
  96 позиций из 1 398 тройников. Загонять туда весь размерный спрос —
  значит спрятать 93% ассортимента.
* **Нет товара — нет рекламы.** Если марки или норматива нет в фасете
  раздела, фразы про них выбрасывать, а не вести на витрину.

## Шаг 5. Семантика: спрос проверять до сборки

```bash
python scripts/ads/direct_atomic.py plan
```

Каждая фраза-кандидат проходит через `keywordsresearch.hasSearchVolume`.
Цифры с PROM-EN, чтобы понимать масштаб отсева:

* по номерам отраслевых стандартов спрос есть у **9%** фраз;
* по маркам сталей — у **77%**;
* по углам отводов — у **77%**.

То есть перебор «норматив × изделие × коммерческая добавка» даёт в основном
мусор, а перебор по свойствам изделия — рабочую семантику.

**Ловушка:** `hasSearchVolume` возвращает строку `"YES"`/`"NO"`, а не
булево. Проверка `if x.get("AllDevices")` пропускает всё подряд, включая
`"NO"`. Сравнивать только с `== "YES"`.

## Шаг 6. Сборка кампании

```bash
python scripts/ads/direct_rebuild.py plan
python scripts/ads/direct_rebuild.py apply
```

Структура, которая работает для промышленного B2B:

* **кампания = раздел каталога**, а не тип объявления;
* **группа = норматив, свойство или диапазон размеров**, 5–200 фраз;
* **посадочная = фасет** там, где признак назван в запросе, иначе витрина
  раздела;
* объявления создаются сразу с уточнениями, организацией, быстрыми
  ссылками и отображаемой ссылкой — задним числом часть из них не
  проставить (см. `api-traps.md`);
* кампания создаётся **остановленной**, старые не удаляются, а
  переводятся в `SUSPENDED`.

Быстрые ссылки делать **тематические под каждую кампанию**, до восьми штук:
четыре в свой раздел каталога, четыре общих (калькуляторы, производство,
проекты, контакты).

## Шаг 7. Сплошной аудит

```bash
python scripts/ads/direct_audit.py
```

44 пункта по каждой кампании со сравнением между ними: расхождения
помечаются стрелкой. Полный разбор пунктов — в `audit-checklist.md`.

Запускать после каждого изменения. Выборочные проверки на этом проекте
трижды подряд пропускали настройку, которую потом находил заказчик.

## Чего API не сделает

* **Стратегию кампаний старше весны 2024** — ошибка 5005 с заглушкой
  `CampaignStub`. Только руками в интерфейсе или пересборкой.
* **Подтверждение прав на организацию и коллтрекинг** — только интерфейс.
* **Загрузку клиентской базы в Аудитории** — отдельный API, см.
  `crm_audience.py`.

## Офлайн-конверсии из CRM

Без них любая конверсионная стратегия учится на отправках формы, включая
спам. Проверять так: отчёт по всем кампаниям с CRM-целями за год. Если
везде ноль — цепочка не работает, и это блокер номер один.

```bash
python scripts/ads/crm_conversions.py --from 2026-09-01
python scripts/ads/offline_conversions.py upload <файл> --dry-run
python scripts/ads/offline_conversions.py upload <файл>
```

Первый берёт из Битрикса качественные лиды и успешные сделки, находит у них
`yclid` или ClientID и складывает в CSV; второй грузит в Метрику. Цель
указывается колонкой `target`, так что лиды и сделки едут одним файлом на
разные цели.

**Что проверить до того, как это заработает** (на PROM-EN сломано и то,
и другое — и лечится регламентом, а не кодом):

* **доходят ли заявки с сайта до CRM.** Лидов с `SOURCE_ID=WEB` за три
  месяца было ноль, весь поток — звонки и письма;
* **создаются ли сделки из лидов.** Если менеджер заводит сделку заново,
  `LEAD_ID` пуст и связь с кликом потеряна навсегда. Из 50 сделок за три
  месяца `LEAD_ID` не было ни у одной.

Метка `ADD_METRICA_TAG` должна быть `YES`: без `yclid` сделку не с чем
связать.

Если основной канал — звонки (для завода это обычное дело), коллтрекинг
важнее веб-форм: он даёт цели по звонкам в счётчике профиля организации.
