# Обход и технический разбор сайта

Два скрипта в `scripts/seo/`: `crawl.py` собирает факты в SQLite,
`report.py` превращает базу в отчёт. Разделены намеренно — обход
дорогой, а отчёты по одной базе гоняются сколько угодно.

Готовый плагин `claude-seo` тут не помощник: у него потолок 500 страниц,
а у нас 15 407 товаров.

## Как запускать

Боевая цель — **новый сайт** `https://prom-en.forgotaboutdre.ru`
(он же будущий prom-en.com). Локальная копия — `http://localhost:8080`,
но она расходится с прод-стендом: коллега правит прод напрямую.

Полный обход по ссылкам (даёт настоящую глубину клика и граф ссылок):

```bash
python scripts/seo/crawl.py https://prom-en.forgotaboutdre.ru --db perf-reports/seo/crawl-new.db --workers 4
```

Добрать то, что есть в sitemap, но не нашлось по ссылкам (ищем сирот):

```bash
python scripts/seo/crawl.py https://prom-en.forgotaboutdre.ru --db perf-reports/seo/crawl-new.db --sitemap --resume
```

Быстрая проверка структуры без товарных карточек:

```bash
python scripts/seo/crawl.py https://prom-en.forgotaboutdre.ru --db /tmp/fast.db --limit 300 --exclude "/catalog/[^/]+/[^/]+/[^/]+/"
```

Отчёт:

```bash
python scripts/seo/report.py --db perf-reports/seo/crawl-new.db --out perf-reports/seo/2026-08-25/
```

Ключи `crawl.py`: `--workers` (4 для шаред-хостинга, 8–12 для локального
докера), `--limit`, `--max-depth`, `--sitemap [url]`, `--resume`,
`--with-query` (по умолчанию URL с `?` пропускаются — иначе фасеты
каталога дадут бесконечный обход), `--include/--exclude` (regex),
`--auth user:pass`, `--ignore-robots`, `--delay`.

Ключи `report.py`: `--check <id>` (одна проверка), `--severity 1`
(только критичное), `--limit` (примеров в консоль), `--out` (markdown + CSV
по каждой проверке).

## Порядок работы

1. Обход по ссылкам, затем добор из sitemap с `--resume`. Без второго
   шага сироты не найдутся — их же не видно по ссылкам.
2. `report.py --severity 1` — сначала только красное.
3. Каждую находку проверить на живом URL, прежде чем чинить: краулер
   видит HTML без JS, и часть «пропавших» H1 может добавляться скриптом.
4. Правки — в теме, не в базе, если это шаблон.
5. Повторный обход в новую базу, сравнить количества.

## Что на этом проекте значат находки

**Дубли title и description** — главный риск. У 15 407 карточек мета
генерируется шаблоном; если в шаблон не подставились размер и ГОСТ,
получаются тысячи одинаковых заголовков, и Яндекс пометит их
«малополезная страница, дубль». Смотреть `dup_title`, `dup_desc`,
`dup_h1` в первую очередь и всегда — на полном обходе, не на выборке.

**Глубина больше 3** на каталоге неизбежна: категория → пагинация
109 страниц → карточка. Это не ошибка вёрстки, это структура. Лечится
не переносом ссылок, а sitemap и перелинковкой популярных позиций,
поэтому `deep` тут читаем как «сколько товаров живёт на отшибе», а не
как список к исправлению.

**Тонкий контент** на карточках нормален (таблица характеристик — не
текст). Обращать внимание, только если тонкая страница ещё и дублирует
мета соседей.

**Сироты** для нас реальны: часть товаров может не иметь входящих ссылок
вообще, если она выпала из фильтров категории.

**`cross_canonical`** на страницах пагинации — ожидаемо и правильно.
На товарных карточках — сигнал тревоги.

## Ограничения

- Не исполняет JS. Если тема рендерит что-то на клиенте, краулер этого
  не увидит — проверять через Browser-панель.
- URL с параметрами по умолчанию пропускаются. Для аудита фасетов
  запускать отдельно с `--with-query --limit 500` и коротким `--include`.
- Базы `perf-reports/seo/*.db` в git не едут (см. `.gitignore`), отчёты —
  едут. Держать их по датам: `perf-reports/seo/ГГГГ-ММ-ДД/`.
