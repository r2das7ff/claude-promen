# Инцидент 23–24.09.2026: сайт недоступен, «Error establishing a database connection»

## Что произошло

| Время (МСК) | Событие |
|---|---|
| 23.09, 19:30 | На каталог пришёл ботнет: ~33 тыс. IP, браузерные User-Agent, без Referer и cookie. Перебирает сочетания фильтров `/catalog/?gost=a,b,c,d&steel=…` — до 5 запросов в секунду |
| 20:00–23:10 | MySQL не справляется: от 20 до 50 % ответов — «Error establishing a database connection» (500) |
| 23:20 | Доступ к базе отрезан полностью: `ERROR 1045 Access denied for user 'promen9917_promen'@'localhost'`. Тикет Timeweb №12709309: «…мы были вынуждены сбросить права доступа базы данных promen9917_promen… После принятия мер сообщите нам для восстановления прав» |
| 24.09, 02:10 | Поток ботов стих (~70 запросов за 10 минут), но база так и осталась закрыта — 500 на всём, кроме страниц из кеша |
| 24.09, ~10:20 | Выложена защита (ниже). Сайт отдаёт кеш, страницу техработ с формой и 503 вместо 500 |
| 24.09, ~10:45 | Выложен предохранитель базы (не больше 4 генераций одновременно). Ответ в тикет — права можно восстанавливать |

За ночь 99 671 запрос, из них **90 703 (91 %) — сочетания двух и более значений
фильтров**, у 99,99 % нет Referer. К API каталога за то же время — 37 запросов:
боты не исполняют JavaScript.

## Почему это стало возможно

1. **Ловушка для краулера в каталоге.** Фишки фильтров — обычные ссылки
   `<a href>` с накопленным выбором (`promen_multi_toggle_url()`): со страницы
   с k фильтрами ведут ссылки на страницы с k+1. Пространство адресов бесконечно.
   `robots.txt` (`Disallow: /*?`) и `noindex` такие боты не читают.
2. **Каждое сочетание — полная генерация.** Полностраничный кеш пропускал мимо
   себя любой адрес с параметрами, а на виртуальном хостинге нет Meilisearch —
   фасеты считаются сканированием таблицы канона в MySQL.
3. **Общий MySQL виртуального хостинга** с лимитом соединений: перегрузка
   одного сайта заканчивается ошибками, а затем блокировкой пользователя БД.
4. **Мониторинг ничего не видел.** UptimeRobot проверял `HEAD /` — главную из
   кеша, — и все 400 проверок за время сбоя получили 200.
5. **При отказе базы сайт отдавал голую ошибку 500** — в том числе на
   отправку заявок. В этот раз обошлось: за время сбоя форму отправляли
   четыре раза, одна заявка (23.09, 21:46) прошла, три отказа с 500 — спам-боты
   (страница и отправка за одну секунду, без стилей и скриптов).

«Каталог не фильтруется» — следствие того же: фильтры работают через
`/wp-json/promen/v1/catalog`, который падал с 500. Код фильтров на проде
совпадает с репозиторием и на стенде работает (проверено в браузере).

## Что сделано (выкладка — [scripts/incident-0924/DEPLOY.md](scripts/incident-0924/DEPLOY.md))

| Мера | Эффект |
|---|---|
| **Проверка браузера для сочетаний фильтров** (`advanced-cache.php`, до WordPress и без базы) | Бот перебора получает 403 на 2 КБ за миллисекунды. Человек — мгновенную перезагрузку (JS ставит cookie `pe_js`). Одиночные фильтры и посадочные Директа (`dn_min/dn_max`, `q`) не затронуты. Отсекает 91 % ночного потока |
| **Предохранитель базы** (`advanced-cache.php`) | Не больше 4 генераций WordPress одновременно (`PROMEN_RENDER_SLOTS`), остальные ждут слот (браузер с cookie сайта — до 8 с, прочие — 1,5 с), затем получают сохранённую копию страницы или 503. Нагрузка сайта на MySQL ограничена сверху при любом трафике — в том числе при обходе кеша, который проверка браузера не ловит. Заявки (POST), админка и расчёт доставки — мимо ограничения. На стенде: 40 параллельных запросов → по 4 одновременно, лишние — копия раздела |
| **Кеш для одиночного фильтра и для адресов с utm/yclid** | `?gost=…`, `?group=…` — конечный набор адресов, теперь из кеша (5 мс против 0,5 с). Клик из Директа отдаётся из кеша чистой страницы: yclid и ClientID скрипт читает из адреса сам |
| **`db-error.php`: сайт переживает отказ базы** | Страница есть в кеше — отдаётся (даже устаревшая) с плашкой «ограниченный режим». Нет — страница техработ с телефоном и формой, код **503 + Retry-After** (поисковики не выкидывают страницы из индекса, в отличие от 500). **Заявки со всех форм сохраняются** в `~/prom-en.com/leads-spool/` (вне сайта) и уходят письмом. API отвечает JSON 503 |
| **`/wp-json/promen/v1/health`** | Мимо кеша, каждый раз спрашивает MySQL и проверяет, что канон каталога не пуст. 200 — живо, 503 — авария |
| **`.htaccess`, блок `promen-guard`** | До PHP: Bytespider, `xmlrpc.php`, `readme.html`, `license.txt`, `*.bak/*.sql/*.log…` → 403 (в корне лежит `wp-config.php.bak`) |

Всё проверено на стенде: имитация отказа БД, проверка браузера в Chrome,
сохранение заявки с вложением и кириллицей, импорт `wp promen leads-spool --import`.
Файлы темы не менялись — кеш страниц при выкладке не сброшен.

## Что нужно сделать вам

**Срочно — ответить в тикет №12709309**, права восстанавливают после ответа:

> Причина нагрузки — бот-атака на сайт вечером 23.09: около 100 тыс. запросов
> с ~33 тыс. IP-адресов перебирали комбинации фильтров каталога, и каждая такая
> страница генерировалась заново с запросами к базе данных. Приняли меры:
> 1) запросы-переборы фильтров отсекаются до запуска PHP-приложения, без
> обращения к БД (91 % того трафика); 2) расширено полностраничное
> кеширование; 3) сайт генерирует не более 4 страниц одновременно, остальные
> запросы получают кешированную копию — нагрузка на MySQL ограничена сверху
> независимо от трафика; 4) заблокированы агрессивные боты и служебные адреса.
> Просим восстановить права пользователя promen9917_promen к базе
> promen9917_promen. Будем следить за нагрузкой по графику.

**В ближайшие дни:**
1. **UptimeRobot**: монитор `https://prom-en.com/wp-json/promen/v1/health`,
   тревога на любой код, кроме 200. Нынешний `HEAD /` аварию не видит.
2. **Почта для заявок при сбое БД**: `define('PROMEN_SMTP_USER', …)` и
   `PROMEN_SMTP_PASS` в `wp-config.php` (ящик no-reply@). Сейчас при отказе базы
   письмо уходит через `mail()`, а IP хостинга нет в SPF — оно может попасть в
   спам. Заявка в любом случае сохраняется в `leads-spool`.
3. **WP-Cron**: `define('DISABLE_WP_CRON', true)` + задача в панели Timeweb
   каждые 5 минут `/opt/php8.3/bin/php ~/prom-en.com/public_html/wp-cron.php`.
   За ночь было 3 997 самозапусков `wp-cron.php` — лишняя нагрузка на базу.
4. **Убрать `wp-config.php.bak` из `public_html`** (сейчас закрыт правилом, но
   держать копию конфига с паролем в корне сайта не нужно).

**Стратегически:** каталог на 15 тыс. позиций с фасетным поиском упирается в
общий MySQL виртуального хостинга. В брифе прод — VPS (Timeweb Cloud 4 CPU / 8 GB,
Redis). На VPS заработают Meilisearch (фасеты перестанут бить по MySQL — код
это уже умеет), объектный кеш, ограничение частоты запросов в nginx.
