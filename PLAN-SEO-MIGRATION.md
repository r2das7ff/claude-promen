индексации (robots.txt разрешает всё). Если он уже в индексе — после переезда
получим два одинаковых сайта и склейку не в ту сторону.

**Три ловушки, найденные при аудите:**

1. **`wp-cli` на проде падает.** Плагин `rustolat` несовместим с PHP 8
   (`strtr()` получает строку вместо массива) и роняет весь WordPress на
   любой команде. Работать только с `--skip-plugins`. Это же объясняет,
   почему сайт до сих пор на PHP ниже 8.2.
2. **Чужие drop-in'ы в `wp-content`**: `advanced-cache.php`, `object-cache.php`,
   `db.php` — это W3 Total Cache. Наш полностраничный кеш пишет в тот же
   `advanced-cache.php`. Перед запуском нового сайта их снять.
3. **`MX 10 mx.yandex.net`** — на домене живёт корпоративная почта.
   При перецепке трогаем **только A-запись**, зону целиком не перезаписываем.

## Этап 1. Карта редиректов (2–3 дня, основная работа)

1.1. **Категории (1 276 шт.)** — сверяются полуручно: список короткий,
     а вес у них максимальный. Каждой старой рубрике — конкретная новая
     категория `/catalog/...`. Часть старых рубрик в новом сайте стала
     фильтром, а не страницей (например «отводы по градусам», «ППУ по ТУ») —
     для них цель редиректа: категория + предустановленный фильтр в URL.
1.2. **Товары (8 888 шт.)** — автоматом: из slug парсится тип + размер +
     ГОСТ/ТУ (`dnishhe-ellipticheskoe-otbortovannoe-133x8-gost-6533-78`),
     ищется товар в новой базе по тем же полям. Совпадения — в карту,
     несовпадения — в ручной разбор.
1.3. **Непокрытые URL** — редирект на ближайшую категорию (не на главную!).
     На главную вести можно только явный мусор. Товары, которых в новой
     номенклатуре нет вообще, — 301 на категорию, 410 не используем.
1.4. **Правила**: только 301, только один хоп (никаких цепочек), никаких
     редиректов на 404 и на страницы с noindex. Файл карты — в git,
     `content/redirects.csv`, ревью глазами по выборке 100 строк.
1.5. **Реализация**: не .htaccess (10k правил в Apache — заметная просадка на
     каждый запрос), а mu-plugin с хеш-картой (`old_path => new_path`), карта
     компилируется в PHP-массив/`opcache`. Промах — обычная 404 темы.

## Этап 2-бис. Нормативные PDF (решения приняты 2026-09-01)

Коллега залил 2026-09-01 в `wp-content/uploads/normativy/` **84 PDF, 106 МБ** —
транслитерированное подмножество локального архива `normatives/` (127 файлов,
156 МБ). Залиты по FTP, **мимо медиатеки WordPress**: в базе их нет ни как
вложений, ни в `wp_options`, ни в мете постов и терминов. По HTTP отдаются
корректно. Тема о папке не знает — ссылок с сайта нет.

**Решения пользователя:** публикуем в свободном доступе (в `robots.txt` не
закрываем); имена чиню я.

2б.1. **Перенести файлы на прод отдельно.** Их нет ни в git, ни локально в
      таком виде — только на стенде. Перенос «тема + дамп базы» их не захватит.
      Сам архив `normatives/` лежит **вне git-репозитория** (репозиторий — это
      `site/`), то есть 156 МБ исходников существуют в одном экземпляре на
      машине пользователя. Забрать в надёжное место до переезда.

2б.2. **Починить имена.** Связывание по имени файла сейчас даёт 404 на трети:

      | | файлов |
      |---|---|
      | совпадают со слагом термина как есть | 30 |
      | + снять ложный префикс `gost-r-` | +9 |
      | + привести год к формату слага | +10 |
      | **свяжется после починки** | **49 из 84** |
      | термина нет ни в каком виде | 35 |

      Две системные ошибки: **19 файлов с префиксом `gost-r-`** там, где это не
      ГОСТ Р (`gost-r-12820-1980`, хотя ГОСТ 12820-80 — не ГОСТ Р), и год
      четырьмя цифрами (`ost-36-21-1977`) против двух в слаге (`ost-36-21-77`).

2б.3. **Связать с шаблоном норматива**: ссылка на документ на странице
      `/normativy/<slug>/` и в блоке нормативов карточки товара. Файла нет —
      блок не рисуем, «битой» ссылки быть не должно.

2б.4. **35 файлов без термина** — разобрать поштучно: часть это смежные
      стандарты (ГОСТ 15150-69 климатика, ГОСТ 30546.х сейсмика), которым
      термина в каталоге и не должно быть. Решение по каждому — с пользователем.

2б.5. **83 термина из 132 остаются без PDF** — зафиксировать список, чтобы
      было понятно, чего дозаливать.

2б.6. Регистрировать ли файлы в медиатеке WP — **нет.** Они отдаются статикой
      по прямому пути, вложения дали бы 84 лишние страницы `?attachment_id=`
      под индексацию. Ссылки строим от слага, без обращения к базе.

## Отложено до переезда (решения приняты, работа не начата)

**Вес карточки товара.** Медиана 590 КБ у труб, 519 у крепежа — это 7 351
карточка из 15 407. Причина: таблица серии рендерится дважды (конфигуратор
`#specTable` и реестр `.series-full`), 501 + 501 строка, а посетитель сразу
видит 32. Обе таблицы видимые и рабочие, удалить нельзя. Вариант — отдавать
с сервера только видимые строки, остальные подгружать через
`inc/catalog-api.php`. Даёт 571 → ~110 КБ. Цена: разворачивание перестаёт
быть мгновенным, скрытые строки уходят из HTML. Затрагивает конфигуратор,
через который идут заявки, — трогать только осознанно.

**Изображения в WebP.** 14,6 МБ ассетов, фотографии проектов лежат в PNG по
мегабайту. Конвертация q82 даёт 56–59% экономии на PNG и 19–37% на JPEG,
суммарно около 7 МБ. Не сделано: 86 вхождений в 15 шаблонах, а дизайн
переносился 1:1.

**109 переходов с одинаковыми концами.** Брак извлечения: `outer_d_branch`
продублирован из основного конца, при этом `execution` разный. Проверено по
ОСТ 34.10.422-90 — таких изделий не существует. Чинится таблицами размеров
из восьми PDF. Это же и остаток дублей title: 122 страницы из 272.

**Объектный кеш на memcached.** Демон на сервере работает. Свой бэкенд писать
не советую — ~400 строк с тонкой семантикой групп; брать поддерживаемый
drop-in и вычитывать код перед установкой.

**4 адреса точёных переходов** из sitemap, до которых не дошёл обход.
