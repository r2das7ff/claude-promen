# Профессиональный аудит каталога PROM-EN

Дата: 2026-07-22 · Метод: чтение кода (file:line) + живые проверки (`localhost:8080`,
`wpcli`, REST). Аудит — только находки и рекомендации; фиксы отдельной задачей.

## Резюме

Каталог инженерно зрелый: канонический индекс-слой (`promen_catalog_rows`),
Meilisearch с SQL-фолбэком, REST-API, per-category колонки, параметризованные запросы
(нет SQL-инъекций), экранирование вывода (нет XSS), физическая валидность почти чистая
(19 из ~45 000). Основные проблемы — **продуктовые/архитектурные, не безопасность**:

- **Поиск сужается до текущей категории** без явного «искать по всему каталогу», и
  релевантность Meili выбрасывается принудительной сортировкой. (подтверждено живьём)
- **Дубликат-дрейф реестр↔лендинг** и **≥4 хардкод-списка категорий** + **3 источника
  истины для counts** (расходятся на ~24 позиции).
- **Фланцы**: каталог-таблица не показывает самые заполненные и важные для покупателя
  поля (Dб 79 %, число болтов 79 %, болт 62 %); карточка выглядит по-разному у разных
  нормативов. Это и есть «хаос», о котором писал пользователь.
- **163 перехода (23 %) и 41 фланец без норматива** в живой БД (колонка «Норматив» = «—»).
- Мёртвые параллельные ветки (WP_Query-фильтры, фолбэк-колонки, `dim_pn_mpa`).

Топ-риск: расхождение «живая БД ↔ логика импорта» — код чинит проблемы на импорте, но в
БД остаются старые артефакты; нет фонового реконсиляции/ребилда как гарантии.

## Что сделано ХОРОШО (не менять)
- **SQL-фолбэк параметризован**: `$wpdb->prepare` + `%s` (`catalog-search.php:415,423,430,437,445,491`) — **инъекций нет**.
- **Экранирование вывода**: `esc_html/esc_attr/esc_url` в рендере строк/ячеек (`catalog-render.php:124-150`) — **XSS закрыт**.
- **Устойчивость движка**: Meili health-check → SQL-фолбэк (`catalog-search.php:522-536`); живьё `engine=meili`.
- **Физ-валидность почти чистая** (19 из ~45 000), колонки раздельные (Dн/s), фильтрованные виды `noindex`.
- **0 «отводов в переходах» сейчас** (жалоба не воспроизводится живьём — вероятно, был кэш браузера; перекhody 728→704 и otvody 3911→3935 указывают, что 24 записи СТО 79814898.110 уже ушли из переходов).

## Раздел «Поиск» (подробно)
Сейчас: форма GET → перехват JS → REST `promen/v1/catalog`. `q` **всегда** AND-ится с
активной группой; на корне `/catalog/` (без group) — по всему каталогу, внутри группы —
только по ней. Релевантность Meili заменяется сортировкой dn/pn/mass/title. SQL-фолбэк —
`payload LIKE '%q%'` (весь JSON-блоб, ложные срабатывания по slug/URL, no-index).

Рекомендуемая целевая модель:
1. **Scope-переключатель** «В этом разделе / По всему каталогу» рядом с полем; по
   умолчанию — весь каталог, с бейджами категорий в выдаче.
2. При 0 результатов в группе — подсказка «N найдено в других разделах →».
3. Для запросов с `q` — сортировка по релевантности Meili; dn-сортировка только когда
   `q` пуст.
4. Заменить `payload LIKE` на индексируемое поле `search_text` (уже строится
   `catalog-document.php:25`) — колонка + `FULLTEXT`/`LIKE search_text`.

## Раздел «Фланцы» (подробно — ответ на «хаос»)
Живая наполненность (822 товара): DN 100 %, PN 85 %, Dн 100 %, **Dб (bolt_circle_d)
79 %**, **число болтов (stud_count) 79 %**, **болт M (bolt_d) 62 %**, толщина b 71 %,
уплотн. поверхность 50 %, ряд 50 %. Каталог показывает лишь DN·PN·Тип·Dн·b·Масса —
самые ценные для подбора поля (Dб, число/размер болтов) **скрыты**.

Предлагаемый **каталог-набор фланцев** (как у конкурентов):
`DN · PN · Тип(человекочитаемый) · Dн · Dб · n×M(болты) · b · Масса`.

Предлагаемая **карточка фланца** (единая по всем нормативам, поля с прочерком если нет):
`DN · PN · D нар · D болт.окр. · d внутр · число болтов n · болт M · толщина b · ряд ·
уплотнит. поверхность · тип · норматив · сталь · масса`.
Плюс:
- Маппинг сырых кодов типа `01/11/ФП/ФВ` → человеческие метки (взять из
  `FLANGE_TYPES` `promen-cli.php:45-50`, сейчас используются только для слагов).
- Убрать дубль/мёртвые PN-поля (`dim_pn_mpa` не выводится, `dim_pn` дублирует `pn`).
- Дописать фланцевые поля в `field_dictionary.csv`.
